# F5.1 · HITL을 반증한다 — 이력이 쥔 것과 놓친 것

## 왜 이 커밋이 생겼나

F3.3은 체크포인터도 `interrupt()`도 없이 승인 게이트를 만들었고, 근거는 한 문장이었다.

> 이 에이전트의 **유일한 상태가 `messages` 채널**이라, 대화만 되돌려주면 체크포인터 없이도
> 정확히 그 자리에서 이어진다.

그 문장에 확인되지 않은 곳이 두 군데 있었다.

**하나는 주석 안에 괄호로 적혀 있었다.** `packages/agent/test/approval.test.ts`의 재개 테스트:

```ts
// **재개에 필요한 건 이력뿐이다.** 새 그래프를 세워도(=프로세스가 죽었다 살아나도) 이어진다.
```

괄호 안의 말을 실제로 해본 적이 없다. 그 테스트는 한 프로세스 안에서 `createAgent`를 두 번
부를 뿐이고, 둘은 메모리를 공유한다. 툴의 `ran` 배열 같은 모듈 변수가 살아 있어서 재개를
은근히 돕고 있어도 알 방법이 없었다.

**다른 하나는 전제의 범위다.** "유일한 상태가 `messages`"는 `createAgent`의 기본값일 뿐이고,
`AgentConfig.schema`는 **F3.1 때부터 열려 있었다.** 채널이 하나만 늘어도 전제가 깨진다.

이 커밋은 아무것도 고치지 않는다. **현재 동작을 못 박아 F5.2가 무엇을 뒤집어야 하는지
남기는 것**이 전부다.

## 사전 예측이 틀렸다 — 두 배가 아니라 증발이다

로드맵(`379e260`)에 이렇게 적어뒀었다.

> 반례: `budget: BinaryOperatorAggregate(+)`를 둔 에이전트로 같은 왕복을 하면 **두 배가 된다.**

**틀렸다.** 두 줄이 그것을 가른다.

```ts
// channels/binop.ts
let acc: T | typeof MISSING = this.value;
for (const v of values) {
  acc = acc === MISSING ? v : this.operator(acc, v);   // 비면 seed, 차면 접는다
}
```

```ts
// pregel/loop.ts — stream()마다 새로 만든다
for (const [key, make] of channelFactories) channels.set(key, make());
```

`CompiledGraph`는 **팩토리 맵만** 들고 있고 값을 안 들고 있다. 그래서 재개 run은 늘 빈 채널에서
시작하고, 입력은 접히는 게 아니라 **그냥 놓인다.** 더할 대상이 없으니 더하지 않는다.

실측(`plan: LastValue`, `budget: BinaryOperatorAggregate(+)`를 단 에이전트):

```
턴 1 최종 상태 키: [ "messages", "plan", "budget" ] | budget = 5
턴 2 스텝: [["tools"],["model"]]
턴 2 최종 상태 키: [ "messages" ] | budget = undefined | plan = undefined
→ 승인 왕복은 돌았나? 예 (툴 결과 1개)
```

**두 배가 아니라 키가 통째로 없다.** `undefined`가 들어간 게 아니다 — `readChannels`가 값 없는
채널을 **아예 안 담기** 때문이다.

### 그리고 이쪽이 더 나쁘다

두 배는 눈에 보인다. 증발은 안 보인다. 여기서 더 고약한 건 **게이트가 완벽히 작동한다**는
점이다 — 스텝은 `tools → model`, 툴은 정확히 한 번 돌고, 대기도 남지 않는다. 아무도
"뭔가 사라졌다"고 말해주지 않는다.

**소리 없는 실패가 시끄러운 실패보다 나쁘다.** F4.1이 접두사 휴리스틱을 접은 이유와 같은
모양이다 — "조용히 틀리고, 그 오염이 정상 행과 구분이 안 된다."

두 배가 되는 위험은 **F5.2 이후에** 생긴다. 체크포인트로 채널을 복원해 놓고 입력까지
주입하면 그때 `operator(3, 3) = 6`이 된다. langgraph가 **복원은 대입 / 입력은 리듀서**로
두 경로를 엄격히 가르는 이유가 정확히 그것이다(`last_value.py`의 `empty.value = checkpoint`,
`binop.py`가 `operator`를 통과시키지 않는 것). 내가 그 위험을 한 단계 앞당겨 말했다.

## 프로세스를 죽였다 살린다

주장이 "재개에 필요한 건 이력뿐"이라면, 증명은 **이력 말고 아무것도 안 넘기는 것**이어야 한다.

`test/fixtures/turn.ts`는 턴 하나만 돌고 죽는 스크립트다. 인자로 JSON을 받고 JSON을 뱉는다.
테스트는 이걸 두 번 spawn하고, 첫 자식이 뱉은 이력을 둘째 자식에게 그대로 넘긴다.
`packages/mcp/test/`가 진짜 stdio 서버를 띄우는 그 패턴 그대로다(`process.execPath`로
PATH 의존을 없애고, stdout은 JSON 전용 통로로 둔다).

**통과했다.** 그리고 한 프로세스 테스트가 못 하던 것을 한다 — 각 자식이 **자기 `ran` 배열만**
증언한다. 첫 자식은 `[]`, 둘째는 `["a.txt"]`. 모듈 변수가 재개를 돕고 있었을 가능성이
메모리째 사라졌다. 주석의 괄호가 이제 근거를 얻었다.

`"deny"` 재개도 `tools`부터 들어간다. 이건 취향이 아니라 정확성 문제다 — 답 없는 `tool_use`를
실은 이력을 모델에게 되보내면 양쪽 프로바이더 포맷 다 400이다.

## 재개가 성립하는 정확한 범위

`messages`가 무사한 건 **id 덕분이 아니다.** 실측으로 못 박았다 — 가짜 모델이 만드는 이력에는
`id`가 하나도 없는데(`ai("", undefined, CALL)`은 id를 안 단다) 재개 후 중복이 안 생긴다.
`addMessages`의 id 교체가 일한 게 아니라, **채널이 새로 만들어져 입력이 그대로 놓였을** 뿐이다.

그러니까 진짜 규약은 이것이다.

> **재개는 클라이언트가 모든 채널을 손으로 이월할 때만 성립한다.**
> `messages`는 늘 전부 다시 싣기 때문에 그 의무를 면제받은 것처럼 보였을 뿐이다.

실제로 세 키를 전부 다시 실으면 살아남는다(테스트로 확인). 숫자 같은 스칼라에는 id도,
"전부 다시 싣는다"는 습관도 없어서 자기교정이 없다.

그리고 실제 경로가 그 의무를 안 진다 — 스튜디오의 `agentTurn`은 `graph.stream({ messages: history })`다.
타입은 전체 상태를 요구하지만 그 경로가 `CompiledGraph<MessagesState>`로 타이핑돼 있어
**구멍이 타입에도 안 보인다.**

## 안 한 것 (정직)

- **아무것도 고치지 않았다.** `src/`는 한 글자도 안 바뀌었고 export도 안 늘었다.
  반례를 `createAgent`로 세운 덕에 `gatedToolNode`·`approvalEntry`·`approvalExit`를
  공개하지 않아도 됐다.
- **오늘 이 문제로 깨지는 그래프는 저장소에 없다.** `AgentConfig.schema`를 넘기는 호출부가
  **0개**다. 잠재적 벽이지 현재 버그가 아니고, 그렇게 적는 게 맞다.
- 승인 게이트는 추가 채널을 **모른다**(`pendingToolCalls`도 `approvalEntry/Exit`도 `messages`만
  읽는다). 예산 초과 같은 걸 게이트가 잡아주지 않는다.

## 덤으로 관찰된 것

**재귀 한도가 왕복마다 리셋된다.** `const limit = 100`이 `stream()` **안에** 있어서, 왕복 N번이면
최대 100N 스텝을 돈다. 스텝 수로 폭주를 막으려는 시도는 지금 구조에선 실패한다.
