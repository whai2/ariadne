# F3.2 · MCP 링 — `@ariadne/mcp`, 툴 정의의 두 번째 입구

## 왜 이 커밋이 생겼나

F3.1이 남긴 벽은 "에이전트가 아는 건 한 번의 자율 루프뿐"이었고, F3의 남은 항목은 셋이었다 —
**세션 · 승인 게이트 · MCP**. 그중 MCP를 먼저 고른 이유는 셋뿐이다.

1. **엔진을 안 건드린다.** F3의 논지("agent = core 위의 특수한 그래프")를 이어갈 수 있다.
   세션은 `ChatModel.invoke` 계약을 흔들고, 승인 게이트는 중단/재개(= core 인터럽트, F4에서
   부딪힐 영속성)를 앞당겨 당긴다. 지금 넣으면 **재개 못 하는 승인**이 된다.
2. **벽이 지금 부른다.** `@ariadne/tools`의 입구는 `defineTool`(zod) 하나뿐이었다. 외부에서
   JSON Schema로 도착하는 툴이 그 전제의 첫 반례다.
3. **`createAgent`가 함수인 이유가 재판받는다.** 노트 21이 "가변 상태·수명주기가 생기면
   클래스로 승격"이라고 적어뒀는데, **열려 있는 연결**이 그 첫 후보다.

도착점 한 줄: **툴 정의의 두 번째 입구.**

```
defineTool(zod)   ─┐
                   ├→ AnyTool ─┬→ toolSpecs() → model.invoke({tools})
mcpTools(server)  ─┘           └→ toolNode()  → 실행
                                  ↑ 여기부터 한 글자도 안 바뀐다
```

## 발견 · 깨질 줄 알았던 전제 둘 중 하나만 깨졌다

계획할 때는 `Tool` 인터페이스를 넓혀야 한다고 봤다. 전제 두 개가 MCP에서 뒤집히기 때문이다.

| | `defineTool` | MCP 툴 | 결과 |
|---|---|---|---|
| spec의 출처 | zod에서 **파생** | 서버의 JSON Schema가 **원본** | **뒤집힌다** |
| `execute` | 로컬 함수 | 다른 프로세스로 가는 **RPC** | 안 깨졌다 |

**②가 안 깨진 게 실측의 수확이다.** `Tool.execute`의 반환이 `unknown`이고 `toolNode`가
`await found.execute(...)`로 부르므로, **비동기 원격 호출이 이미 계약 안에 있었다.** F2.2에서
"툴은 무엇이든 돌려줄 수 있다"로 열어둔 게 여기서 값을 했다.

**①은 진짜 뒤집힌다.** 그런데 이것도 인터페이스를 안 넓혀도 된다 — `Tool`이 `schema`(검증용
zod)와 `spec`(모델이 보는 선언)을 **처음부터 별개 필드**로 갖고 있었기 때문이다. `defineTool`이
둘을 한쪽에서 파생시켰을 뿐, 인터페이스는 방향을 강요하지 않았다. MCP 쪽은 `defineTool`을
안 거치고 두 필드를 직접 채운다:

```ts
schema: z.fromJSONSchema(def.inputSchema)   // 검증용 — 되돌려 만든다
spec:   { …, parameters: def.inputSchema }  // 와이어 — 서버 원본 그대로
```

그래서 **`@ariadne/tools`는 이 커밋에서 한 줄도 안 바뀌었다.** `toolNode`·`toolsCondition`·
`createAgent`·엔진도 전부 무수정이다.

### `z.fromJSONSchema`가 있다는 게 전제였다 (zod 4.5)

이 설계의 성립 조건이다. 없었으면 검증을 포기하거나(→ `schema`를 옵셔널로 넓히고 `toolNode`에
분기 추가) JSON Schema 검증기를 따로 들여야 했다. 실측으로 확인한 것:

- `{type:"object", …}` → **`z.ZodObject` 인스턴스**로 온다(`Tool.schema`가 요구하는 타입).
- `anyOf` · `$ref`/`$defs` · `format` · `contentEncoding` 같은 것들도 통과했다.
- 못 하는 게 나오면 **던진다** → `McpToolSchemaError`가 **툴 이름을 실어** 다시 던진다.
  서버 하나가 툴 20개를 주는데 "변환 실패"만 뜨면 어디를 볼지 알 수 없다.

### 왕복시키면 안 된다 (실측)

되돌린 zod에서 JSON Schema를 다시 뽑으면 원본과 **다르다**:

```
서버 원본 : {"type":"integer","minimum":1}
왕복 결과 : {"type":"integer","minimum":1,"maximum":9007199254740991}
```

모델에게 갈 선언은 **서버가 의도한 계약**이어야 하므로 `spec.parameters`에 원본을 그대로 싣고,
zod는 오직 "모델이 보낸 인자가 그 계약에 맞나"를 우리 쪽에서 보는 데만 쓴다. 테스트가 이걸
`toEqual`로 못박는다.

## 판단 · 왜 `@ariadne/tools`에 안 넣었나

넣었으면 순수했던 툴 링이 **자식 프로세스 · JSON-RPC · 연결 수명**을 지게 된다. 툴을 zod로 적는
사람은 그걸 몰라도 된다. 의존 방향은 `mcp → tools` 한 방향이고 tools는 mcp를 모른다 —
F2.2가 정한 링 규칙 그대로다. (`agent → {model, tools}`가 낸 예외와 같은 종류: **엮는 게 존재
이유인 링만 여럿을 안다.**)

패키지 안도 두 층으로 갈랐다.

| 파일 | 층 | 아는 것 |
|---|---|---|
| `protocol.ts` · `client.ts` | 프로토콜 | stdio JSON-RPC만. **툴 링을 모른다** |
| `tools.ts` | 다리 | 여기만 두 링을 다 안다 |

그 덕에 나중에 리소스·프롬프트가 필요해져도 클라이언트는 제자리에 있다.

## 판단 · SDK를 안 쓴다

`@modelcontextprotocol/sdk` 대신 stdio JSON-RPC를 직접 짰다. F1.7에서 `claude` CLI를
220MB SDK 대신 `spawn`으로 부른 것과 같은 판단이다 — 우리가 쓰는 표면이 **`initialize` ·
`tools/list` · `tools/call` 셋뿐**이라, 감싼 패키지를 들이면 **배우려는 프로토콜이 정확히 그 안에
숨는다.** (HTTP/SSE 트랜스포트와 OAuth가 필요해지면 그때는 SDK가 값을 한다. 거긴 다시 짤 이유가
없는 분량이다.)

프레이밍에서 하나 배웠다: **MCP stdio는 LSP와 다르다.** LSP의 `Content-Length:` 헤더가 아니라
**개행으로 나뉜 JSON 한 줄**이다. 그래서 `splitFrames`가 순수 함수로 떨어지고(누적 버퍼 →
완성 프레임들 + 남은 꼬리), 프로토콜 테스트가 프로세스 없이 돈다.

## 판단 · `isError`는 던지지 않는다 (F2.2 정책이 갈리는 자리)

F2.2가 정한 에러 정책은 둘이었다 — **모델이 잘못 준 인자는 메시지로 돌려주고, 툴 본문이 던지면
전파한다.** MCP는 여기에 세 번째를 끼워 넣는다.

| 무엇 | MCP에서 오는 모양 | 우리 처리 |
|---|---|---|
| 모델이 인자를 틀림 | (서버까지 안 감) | zod가 우리 쪽에서 막아 메시지로 |
| **툴 실행 실패** | `result.isError === true` | **메시지로 (status: "error")** |
| 프로토콜/연결 실패 | JSON-RPC `error` · 프로세스 종료 | **던진다** |

가운데가 F2.2의 "던진다"와 갈리는데, **갈리는 게 맞다.** MCP는 이 필드를 *모델에게 보여주라고*
만들었다(스펙이 명시한다). 원격 툴의 실패는 우리 버그가 아니라 모델이 다음 수로 고칠 수 있는
사실이다. 데모 서버의 `divide(1, 0)`이 그 장면이다 — 실패 → 모델이 `divide(1, 2)`로 고침.

`status: "error"`를 실으려면 결과 메시지를 **우리가 직접 지어야** 해서 `Command`로 돌려준다.
`ToolContext.toolCallId`가 F2.2에 왜 있었는지가 여기서 처음 쓰인다.

## 발견 · 가변 상태는 에이전트가 아니라 **연결**에 있었다

노트 21은 "세션·MCP·승인 게이트가 붙어 `this`에 얹을 게 생기면 `createAgent`를 클래스로
승격한다"고 적었다. 실제로 붙여보니 **얹을 게 에이전트에 안 생겼다.** 자식 프로세스 · 읽다 만
버퍼 · 답을 기다리는 요청 표 · 닫아야 하는 수명 — 전부 `McpClient` 안이다.

```ts
const server = await connectStdio({ command: "bun", args: ["my-server.ts"] });
const agent = createAgent({ model, tools: [...local, ...(await mcpTools(server))] });
await server.close();          // ← 수명의 주인은 여기다. 에이전트가 아니다.
```

그래서 **`McpClient`가 이 저장소의 첫 클래스**가 됐고, `createAgent`는 계속 상태 없는 함수다.
"클래스로 승격"의 조건이 *기능이 늘어남*이 아니라 *감출 상태가 실제로 생김*이라는 걸 한 번 더
확인한 셈이다.

## 같은 "MCP"인데 F2.4가 거부한 그 MCP가 아니다

노트 20에서 MCP를 한 번 **거부**했었다. 그때 거부한 건 `claude --mcp-config`, 즉 **툴 루프를
claude 프로세스 안으로 넘기는** 경로였다 — 스텝이 안 보이고 워크플로우 제어를 놓친다.

이번은 방향이 반대다. **우리가 클라이언트**라 서버에서 오는 건 툴 목록과 실행 결과뿐이고,
호출 결정은 모델이 · 실행은 `toolNode`가 · 라우팅은 우리 엔진이 한다. 루프는 우리 안에 남는다
(F2.4가 지킨 핵심). 정리하면 MCP에는 방향이 셋 있고 우리는 첫째만 했다.

| 방향 | 우리 역할 | 상태 |
|---|---|---|
| 서버의 툴을 쓴다 | client | **이 커밋** |
| 우리 에이전트/툴을 남에게 노출 | server | VISION 4번 "연동" — 나중 |
| 모델에게 MCP를 통째로 위임 | (없음) | **F2.4가 거부** |

## 테스트가 진짜 서버를 띄운다

가짜 클라이언트를 상대로 테스트하면 **우리가 상상한 서버만 통과한다.** 그래서
`test/fixtures/demo-server.ts`에 스펙대로 된 stdio MCP 서버를 한 벌 짰다(툴 둘: `echo`,
0으로 나누면 `isError`인 `divide`). 프로세스 경계 · 프레이밍 · 핸드셰이크가 전부 진짜로
일어나면서도 **네트워크 0 · 자격증명 0**이라 오프라인에서 `verify`가 그린이다.
(F2.2의 "가짜 모델" 판단과 같은 이유 — 검증 대상이 프로토콜이라 결정론적이어야 관찰이 된다.)

`crash-server.ts`는 가장 흔한 실패 모드를 재현한다: **설정은 맞는데 서버가 안 뜨는 경우.**
이때 `#watchExit`이 없으면 응답이 영영 안 와서 조용한 hang이 된다 — 프로세스 종료를 **에러로
바꿔주는 자리**가 반드시 있어야 하고, 그 에러에 **stderr를 실어야** 진짜 원인이 보인다.

## 안 한 것 (정직)

- **요청 타임아웃.** 프로세스가 죽으면 깨우지만, **살아 있으면서 답을 안 하는** 서버는 매단다.
  두 번째 소비자가 부를 때.
- **`notifications/tools/list_changed` 구독** — 툴 목록은 `mcpTools()` 시점에 굳는다.
- **HTTP/SSE 트랜스포트 · OAuth** — SDK가 값을 하는 자리(위 판단 참조).
- **리소스 · 프롬프트 · 샘플링 · elicitation.** `initialize`에서 능력을 **하나도 선언 안 한다** —
  안 되는 걸 된다고 말하면 서버가 그걸 부른다.
- **이름 충돌 정책.** 서버 둘이 같은 이름을 주면 `toolNode`의 Map에서 나중 것이 이긴다.
  접두사를 붙이면 모델이 보는 이름이 서버 문서와 어긋나므로, 부딪히는 쪽이 고르게 둔다.
- **멀티모달.** 이미지·오디오 블록은 `[image image/png]` 표식으로 접힌다(`ToolMessage.content`가
  string). **버리진 않는다** — 조용히 사라지면 모델이 툴을 다시 부른다. F2.1의 멀티모달 빚이
  여기서 두 번째로 청구됐다.
- **스튜디오 연동** — 사이드바에서 MCP 서버를 붙이는 건 별도 커밋(Studio 트랙).

## 벽 → 다음

원격 툴이 우리 루프에서 도는데, **어느 툴이 원격인지 아무도 안 알려준다.** 스튜디오는
`createAgent`가 만든 그래프를 그대로 관찰하므로 MCP 툴도 그냥 툴로 보인다 — 로컬 툴과 구분이
없는 게 이 커밋의 성과지만, 관찰 도구에서는 **어느 서버에 붙었고 그게 살아 있나**가 보여야 한다.
그리고 아직 사람이 **툴 실행을 막을 자리가 없다** — 남의 프로세스가 파일을 지우는 툴을 줄 수
있는데도. 그게 F3의 남은 둘(승인 게이트 · 세션)이 부르는 자리다.
