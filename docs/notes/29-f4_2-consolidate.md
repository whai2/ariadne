# F4.2 · 공고화와 주입 — 쌓인 것이 문장이 되어 모델에게 간다

## 왜 이 커밋이 생겼나

F4.1이 남긴 벽은 한 줄이었다 — **재료는 쌓였는데 아무도 안 읽는다.** `write_note` 거부가 2회
기록돼 있어도 다음 턴의 모델은 그걸 모른다.

이 커밋에서 **목표 장면이 돈다**: 위험한 툴을 두 번 거부하면, 세 번째 턴엔 모델이 툴을 바로 안
부르고 먼저 묻는다.

## 발견 · **`createAgent`도 core도 안 고쳤다**

이게 이 커밋에서 제일 중요한 사실이고, 계획 단계에서 가장 오래 붙들었던 질문이기도 하다.

계획은 그래프에 `recall` 노드를 붙이고 `memories` 채널을 새로 두려 했다. 그러려면 `createAgent`가
노드를 꽂을 자리를 열어줘야 하고, 그건 agent 링이 memory를 알게 된다는 뜻이었다.

**셋 다 안 했다.** 이미 열려 있는 길이 있었기 때문이다.

```
composeSystem(def.system, facts)
  → AgentConfig.system
  → model.invoke(messages, { system })          agent.ts:142-145
  → [config.system, options.system, …].join()   claudeCode.ts:390-397
  → 프로바이더의 system 자리
```

즉 **메모리 주입은 새 노드도, 새 채널도, 새 실행 개념도 아니라 문자열 합치기다.**

그리고 이게 우연이 아닌 게 — **F4.0 실험이 측정한 경로가 정확히 이것**이다. 실험은 system에
문장 하나를 넣고 행동을 쟀고, 구현은 그 실험을 그대로 재생한다. 노드로 만들었으면 실험과 구현
사이에 **검증 안 된 층이 하나** 끼었을 것이다.

테스트가 이걸 못박는다 — *"사실을 줘도 그래프 모양은 안 바뀐다"* (`getGraph()` 결과가 동일).

### 안 고른 길 · `messages`에 system 메시지를 끼우기

어댑터 셋이 전부 `role:"system"` 메시지를 프로바이더 system 자리로 올리므로 이 길도 열려 있었다.
**지뢰였다.** `agentTurn`이 새 메시지를 **위치로** 자른다:

```ts
produced = final.slice(history.length);   // agents.ts
```

여기에 메시지를 끼우면 잘리는 자리가 어긋나고, 클라이언트 이력에 눌어붙어 매 턴 재전송된다.
무상태 규약(F3.3)이 주입 경로를 하나로 좁혀준 셈이다.

## 판단 · 후보를 **셋** 만든다 (그리고 하나만 쓴다)

`proposeFacts`는 툴 하나마다 **추상화 수준이 다른 문장 셋**을 만든다.

| level | 문장 | F4.0 실험의 예측 |
|---|---|---|
| `episodic` | "사용자는 write_note 실행을 **거부한 적이 있다 (2회)**." | **효과 0** |
| `preference` | "사용자는 write_note이(가) 확인 없이 실행되는 것을 **원하지 않는다**." | 효과 있음 |
| `rule` | "write_note을(를) 부르기 전에 **먼저 설명하고 확인을 받아라**." | 효과 있음 |

**`kind`(의미/절차) 컬럼은 없다.** F4.0이 형식은 무관하다는 걸 실측으로 보여줬으므로 근거가 없다.
대신 `level`을 두는데, **순위에는 안 쓴다** — 무엇이 살아남을지는 사용이 정한다(F4.3). 지금 이
컬럼이 있는 이유는 단 하나, **"사건형이 도태되는 것"을 관찰하기 위해서**다.

그런데 이번 커밋은 **선호형 하나를 손으로 고른다.**

```ts
const facts = memory.facts(def.id).filter((f) => f.level === "preference");
```

**이게 이 커밋의 정직한 한계다.** 실험 결과를 코드에 하드코딩한 것이고, 기계는 아직 아무것도
안 배웠다. 그게 다음 단계의 벽이다.

## 판단 · 왜 LLM을 안 쓰나

생성기가 규칙 기반이다. 검증하려는 게 **문장의 품질이 아니라 루프가 도는가**라서, 값싸고
결정론적인 쪽이 맞다.

더 중요한 건 이 구조가 말하는 바다 — **생성기는 부품이고 선택이 프레임워크다.** 나중에 이
함수만 LLM으로 갈아 끼울 때 나머지가 안 바뀌는 것이 그 증거가 된다.

템플릿이 **툴 이름만** 쓰는 것도 같은 이유다. "write_note는 메모를 저장한다" 같은 사람 말 표를
두면 툴이 늘 때마다 손으로 채워야 하고, 자동화하려면 LLM이 필요하다. 어색해도 이름만으로 만든다.

## 판단 · 임계 두 개

```ts
if (deny < DENY_THRESHOLD || deny <= allow) continue;   // 2회 이상 AND 거부 > 허용
```

- **1회는 사고일 수 있다.** 실수로 눌렀거나, 그때 그 파일만 싫었거나.
- **대개 허용하는 툴이면 그건 선호가 아니다.** 한 번 거부했다고 그 뒤 열 번 승인한 툴을 막으면
  **기억이 사람을 돕는 게 아니라 방해한다.** 메모리 설계에서 이게 제일 쉽게 잊히는 조건이다.

## 판단 · 공고화가 **턴 시작**에 돈다

"유휴 시 배치"는 타이머라는 **새 수명주기**를 부르는데, 그 개념이 지금 답하는 질문이 없다.
두 번째 턴에서 거부가 2회 쌓이면 **세 번째 턴 시작 시** 굳으므로 목표 장면이 그대로 성립한다.

부작용 하나: `GET /api/memory`를 2턴 직후에 보면 **사실이 아직 없다.** 실측에서 실제로 겪었다 —
3턴을 돌린 뒤에야 나타난다. 관찰 창구가 한 턴 늦는 셈인데, 지금은 그게 비용보다 싸다.

## 판단 · 멱등을 플래그가 아니라 `UNIQUE`로

`value_events`에 `consolidated` 플래그를 다는 대신 **매번 전체를 다시 집계하고
`INSERT OR IGNORE`** 한다. `UNIQUE(agent, text)`가 멱등을 준다.

이득이 둘이다.
- **상태를 하나 덜 만든다.** "어디까지 했나"를 아무도 안 들고 있어도 된다.
- **이미 도태된 사실이 부활하지 않는다.** 재공고화가 기존 행을 안 건드리므로 선택 기록(F4.3)이
  그대로 산다.

그리고 `CREATE TABLE IF NOT EXISTS`뿐이라 **기존 DB 파일에 `facts`가 그냥 붙는다** — 마이그레이션
개념(버전·`ALTER`)이 아직 이 저장소에 없다.

## 발견 · 사건형만 계속 늘어난다

테스트를 쓰다 나온 성질이다. 거부가 3회가 되면:

```
사용자는 write_note 실행을 거부한 적이 있다 (2회).   ← 남아 있고
사용자는 write_note 실행을 거부한 적이 있다 (3회).   ← 새로 생긴다
```

선호형·규칙형은 문장이 안정적이라 한 번만 생기는데, **사건형은 횟수가 문장에 박혀 있어 매번
새 행이 된다.** "사건은 일반화가 안 된다"는 게 스키마 층에서 한 번 더 드러난 셈이다.

지금은 그대로 둔다 — 도태 기계(F4.3)가 생기면 이 잉여가 **저절로 정리되는지**가 좋은 시험이 된다.

## 검증

- `bun run --filter '@ariadne/memory' example:loop` — **자격증명 0 · 네트워크 0 · 파일 0.**
  1회 거부(후보 0) → 2회 거부(후보 3) → 다음 턴 system 출력 → 허용이 쌓이면 새 후보 0.
- 테스트 +13 (memory 16 → **29**, studio 57 → **64**): 임계 둘 · 후보 셋의 수준 · `origin` 근거 ·
  툴별 집계 · 에이전트 격리 · 멱등 · **재공고화가 기존 행을 안 건드림** · `UNIQUE`/`CHECK` ·
  `composeSystem`이 맨 뒤에 붙음 · **사실을 줘도 그래프 모양이 동일**.
- **손으로 (진짜 모델, API 키 0):** 스튜디오 `mcp` 에이전트에 메모 저장을 2회 요청 → 2회 거부 →
  3번째 턴:

  ```
  pending: []
  steps:   [['model']]          ← 툴 노드에 아예 안 갔다
  ai: **확인 요청**: 아래 내용으로 메모를 저장할까요?
      - 제목: 회의  - 내용: 3시
  ```

  같은 요청이 F4.1까지는 곧바로 `write_note`를 불러 멈췄다. **기억이 행동을 바꿨다.**
- `bun run verify` 그린: **364 pass / 4 skip / 0 fail** (core 81 · **memory 29** · tools 28 ·
  mcp 37 · model 105 · agent 20 · studio 64). **memory·studio 밖 다섯 패키지 무수정.**

## 안 한 것 (정직)

- **선택 기계** — 지금은 `level === "preference"`를 손으로 고른다. F4.3.
- **감쇠·망각** — 사실이 한 번 생기면 안 지워진다. 도태가 없으니 아직 지울 근거도 없다.
- **툴별 사람 말 표** — 템플릿이 툴 이름만 쓴다. 문장이 어색한 건 알고 있고, 고치려면 LLM이나
  손표가 필요한데 둘 다 이 커밋 밖이다.
- **검색** — 사실이 몇 개뿐이라 전부 싣는다. 수십 개가 되면 그때 고른다.
- **스튜디오 Memory 화면** — 관찰 창구는 여전히 `GET /api/memory`다. 선택 기록까지 생긴 뒤
  한 번에 만든다.

## 벽 → 다음

후보 셋을 만들어 놓고 **`preference`를 손으로 골랐다.** 무슨 근거로? F4.0 실험 결과를 **코드에
하드코딩**했을 뿐이고, **기계는 아직 아무것도 안 배웠다.** 이 에이전트에서 어느 수준이 실제로
쓸모 있는지는 아무도 모른다 — 실험은 한 과제·한 모델에서 잰 것이다.

F4.3이 그 하드코딩을 걷어낸다. 한 턴에 사실 **하나만** 시험하고(동시에 넣으면 귀속이 안 된다),
결과로 강화·감쇠한다. **검증은 사건형 후보가 실제로 도태되는 것** — F4.0이 답을 이미 알고 있으니,
기계가 스스로 거기 도달하는지가 시금석이다.
