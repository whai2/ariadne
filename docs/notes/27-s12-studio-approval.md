# S12 · 스튜디오 승인 UI — 사람이 루프 **사이**에 서는 자리

## 왜 이 커밋이 생겼나

F3.3이 링에 게이트를 만들었지만 **누를 버튼이 없었다.** 정책을 코드로 꽂아야만 사람이 개입할 수
있었고, 스튜디오에서 멈춘 run은 그냥 **빈 응답**으로 보였다. 이 커밋은 그 멈춤을 화면에 올린다.

도착점 한 줄: **툴이 도는 걸 사람이 막을 수 있다.**

## 발견 · 재개에 새 엔드포인트가 안 생겼다

`POST /api/agents/chat`에 필드 **하나**가 늘었다.

```
{ id, messages }                      // 보내기
{ id, messages, decision: "allow" }   // 재개
```

그게 전부다. 세션 id도, `/resume` 경로도, 서버 쪽 대기 테이블도 없다. F3.3 노트가 "재개 = 같은
이력으로 새 run"이라고 적은 것의 HTTP 판이고, 성립하는 이유도 같다 — **상태가 전부 `messages`이고
그걸 클라이언트가 쥐고 있다.** 스튜디오가 S5부터 지켜온 무상태 규약("이력 전체를 받고 새로 생긴
것만 돌려준다")이 **고칠 필요 없이 그대로 재개 규약이 됐다.**

UI 쪽에서도 같은 일이 일어났다. 보내기와 재개가 **같은 함수**다:

```ts
const send   = (text) => turn([...convo, { role: "human", content: text }]);
const decide = (d)    => turn(convo, d);
```

## 판단 · 응답에 `pending`을 실어야 했다

이 커밋에서 **유일하게 새로 생긴 계약**이다. 멈추면 새 메시지가 **하나도 안 늘어나므로**
(F3.3: "ask는 아무것도 안 쓴다"), 그 필드가 없으면 클라이언트는 **멈춤과 빈 응답을 구별할 수 없다.**
링의 `pendingToolCalls(final)`를 `AgentReply`에 그대로 실어 보낸다.

즉 링에서 "아무것도 안 쓴다"로 표현한 멈춤이, 경계를 넘을 때는 **명시적 필드**가 되어야 했다.
같은 사실을 안쪽에서는 부재로, 바깥에서는 존재로 표현한다 — 경계에서 타입이 지워지기 때문이다.

## 판단 · `AgentDef.approval`은 함수가 아니라 **문자열 배열**

링이 받는 건 `ApprovalPolicy`(함수)인데 등록 목록엔 이름 배열을 둔다. 등록 목록은 사이드바로
**직렬화돼 나가야 하기** 때문이다(`AgentInfo`). 그래서 선언과 실행이 갈린다 —
`buildAgentGraph` 한 곳에서만 `askFor(names)`로 함수가 된다.

**S11의 `mcp` 필드와 정확히 같은 모양이다**: 선언(`StdioServerConfig`)은 배열에, 연결은
`connectMcpAgents`에. 두 번 같은 모양이 나왔으니 이건 이 앱의 규칙이다 —
**등록 목록엔 데이터만, 살아있는 것은 부팅 코드에.**

## 판단 · 한 번의 승인은 그 묶음만 연다

```ts
function approvalPolicy(names, decision) {
  const gate = askFor(names);
  let once = decision;              // 대기 중이던 그 묶음에만 쓰고 버린다
  return (calls) => { if (once === undefined) return gate(calls);
                      const a = once; once = undefined; return a; };
}
```

재개하면 START가 `tools`로 들어가므로 **게이트의 첫 호출이 곧 사람이 답한 그 묶음**이다.
`decision`을 계속 물려두면 같은 run 안에서 모델이 또 위험한 툴을 불러도 안 물어본다 —
한 번의 승인이 그 뒤를 전부 열어주는 건 게이트가 아니다.

클로저 상태가 요청 사이에 안 새는 건 `agentTurn`이 **매 턴 그래프를 새로 세우기** 때문이다.
(캐시했으면 이게 버그였다. 안 캐시한 게 여기서 값을 했다.)

## 판단 · `"ask"`는 클라이언트가 못 보낸다

`decision`은 `"allow" | "deny"`만 받고 그 외는 400이다. `"ask"`는 "사람에게 묻겠다"는 뜻인데
요청을 보낸 쪽이 이미 사람이라, 받아주면 **무한 왕복**이 된다.

## 판단 · 안 붙은 툴은 "승인 필요"에서 뺀다

`agentInfo`가 `def.approval`을 **실제로 붙은 툴로 교차 검증**한다. MCP 서버가 안 떠서 툴이 비면
"이 툴은 승인이 필요합니다"가 거짓말이 되기 때문이다(S11의 "한 서버가 안 떠도 스튜디오는 뜬다"와
짝을 이루는 정직함). 같은 이유로 툴이 0개면 게이트 자체를 안 건다 — 링이
`ApprovalWithoutToolsError`로 던지고, 그게 맞다.

## 무엇이 화면에 보이나

| | |
|---|---|
| 툴 칩 | 승인 대상은 `🔒 write_note`(경고색), 나머지는 `🛰 get_weather` — **부르기 전에** 어느 툴이 사람을 부르는지 보인다 |
| 그래프 | 게이트가 붙으면 **점선만 남는다**(정적 엣지 0) — `START⇢tools`(재개)와 `tools⇢END`(멈춤)가 그림에 그대로 나온다 |
| 승인 패널 | 대기 중인 호출을 인자까지 보여주고 `승인하고 실행` / `거부` |
| 스텝 | 멈춘 턴은 `Step 0: model → Step 1: tools`인데 **messages가 안 늘어난다** — "아무것도 안 썼다"가 관찰된다 |

멈춰 있는 동안 **컴포저가 잠긴다.** 대기를 무시하고 다음 말을 보내면 답 없는 `tool_use`를 실은
이력이 모델에게 가고, 그건 양쪽 와이어 포맷 다 400이다. UI가 그 상태를 못 만들게 막는다.

## 데모 서버에 쓰기 툴을 하나 더 줬다

`write_note` — **부수효과가 있는 툴**이라야 게이트가 뭘 막는지 보인다. 진짜 디스크를 건드리는 건
기성 `filesystem` 서버가 맡고, 데모 쪽은 메모리면 충분하다: 보여주려는 게 "무엇이 파괴되나"가
아니라 **"승인 전에는 안 돈다"**라서. 덕분에 게이트 데모가 **오프라인·키 0**으로 돈다.

## S11의 회피를 거둔다

노트 25가 `filesystem` 에이전트를 `mcp-sample/` 한 폴더로 좁힌 걸 "정책이 아니라 회피"라고 적었다.
이제 정책이 생겼다 — `write_file`·`edit_file`·`create_directory`·`move_file`이 승인 대상이다.
**폴더 범위는 그대로 둔다**(게이트가 생겼어도 이중 방어는 남긴다). 회피가 회피가 아니게 된 건
이제 그게 **유일한 방어가 아니기** 때문이다.

**어느 툴이 위험한지 서버는 안 알려준다.** MCP에 그런 필드가 없어서 목록은 우리가 손으로 적는다.
정직하게 적어둘 값어치가 있는 한계다 — 서버가 툴을 늘리면 우리 목록이 뒤처진다.

## 검증

- 오프라인 계약 4: 승인 목록이 실린다(읽기 툴은 안 걸린다) · 안 붙은 툴은 빠진다 ·
  **게이트 그래프엔 정적 엣지가 0이고 노드는 게이트 없는 쪽과 같다** · `decision`은 allow/deny만.
- **진짜 모델로 멈춤·재개 2**(`claude` CLI 있을 때만, API 키 0): 쓰기 툴 앞에서 멈추고
  `pending`에 그 툴이 실린다 → 재개하면 `steps[0].nodes === ["tools"]`(model을 안 부른다) →
  툴 결과가 붙는다. 거부하면 `status:"error"` 결과가 붙고 모델이 다른 길을 찾는다.
- **헤드리스 크롬으로 UI 실제 렌더 확인** — 승인 패널이 뜨고, 승인 버튼을 누르면 툴 결과가
  붙는 것까지 클릭으로 확인.
- **진짜 기성 서버로 손 확인**(`filesystem`): "메모 저장해줘" → 모델이 먼저 안전한
  `list_allowed_directories`를 **조용히** 돌고(게이트 대상이 아니라서) 그다음 `write_file`에서
  멈췄다. 거부 → 파일 **안 생김**, 모델이 대안 제시. 같은 대기에서 승인 → 파일 생성.
  게이트가 한 묶음만 열고 닫힌다는 게 손으로도 확인됐다.
- `bun run verify` 그린: **315 pass / 4 skip / 0 fail** (studio 46 → **52**).

## 안 한 것 (정직)

- **호출별 승인**(하나는 되고 하나는 안 되고) — F3.3의 묶음 판단 그대로.
- **인자를 고쳐서 승인** — 모델이 한 말을 우리가 고치는 거라 별도 판단이 필요하다.
- **거부 사유 입력** — 링의 `Approval`이 문자열 유니언이라 실을 자리가 없다.
- **승인 이력** — 무엇을 언제 승인했는지 안 남는다. 감사 로그가 필요해지면 그건 메모리 링 쪽 일이다.
- **위험 툴 자동 판별** — 이름 목록을 손으로 적는다. 서버가 안 알려주므로 자동화하려면 추측이 된다.

## 벽 → 다음

승인이 **한 run 안에서만** 산다. 대화를 새로 고치면 지금까지 뭘 승인했는지 아무도 모르고,
같은 툴을 또 물어본다("이번만 허용"은 되는데 "항상 허용"이 안 된다). 그걸 하려면 **대화가 아니라
사용자에게 붙는 상태**가 필요하고, 그건 서버가 대화를 소유해야 한다는 뜻이다 — F3.3이
"재개는 클라이언트가 이력을 쥐고 있어서 된다"고 적어둔 전제가 여기서 처음 압박을 받는다.
그게 F3의 마지막(**세션**)이자 **F4 메모리 링**이다.
